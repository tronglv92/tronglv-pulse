# Technical Planning and Implementation Strategy

When researching, analyzing, and creating implementation plans for features, architectures, or technical solutions, follow these guidelines.

## Core Principles

Operate by the holy trinity of software engineering:
- **YAGNI** (You Aren't Gonna Need It)
- **KISS** (Keep It Simple, Stupid)
- **DRY** (Don't Repeat Yourself)

## Mental Models

- **Decomposition**: Breaking huge, vague goals into small, concrete tasks
- **Working Backwards**: Starting from desired outcome and identifying every step to get there
- **Second-Order Thinking**: Asking "And then what?" to understand hidden consequences
- **Root Cause Analysis (5 Whys)**: Digging past surface-level requests to find the real problem
- **80/20 Rule (MVP Thinking)**: Identifying 20% of features that deliver 80% of value
- **Risk & Dependency Management**: Asking "What could go wrong?" and "Who/what does this depend on?"
- **Systems Thinking**: Understanding how new features connect to or break existing systems
- **Capacity Planning**: Thinking in terms of team availability for realistic deadlines
- **User Journey Mapping**: Visualizing user's entire path to ensure complete solution

## Plan Structure

Every implementation plan should include:

1. **Problem Statement**: Clear description of what needs to be solved
2. **Requirements Analysis**: Functional and non-functional requirements
3. **Proposed Solution**: Detailed technical approach with alternatives considered
4. **Implementation Phases**: Step-by-step breakdown of work
5. **Dependencies**: External dependencies and prerequisites
6. **Risks**: Potential issues and mitigation strategies
7. **Success Criteria**: How to measure successful completion
8. **Timeline**: Realistic estimates for each phase

## Planning Process

1. **Understand Requirements**: Fully grasp user needs and business objectives
2. **Research**: Investigate best practices, existing solutions, and technical constraints
3. **Design**: Create comprehensive technical design with alternatives
4. **Break Down**: Decompose into manageable, concrete tasks
5. **Validate**: Ensure plan is feasible, complete, and addresses all requirements
6. **Document**: Create clear, actionable plan documentation

## Quality Standards

- Plans must be actionable and specific
- Include concrete tasks, not vague goals
- Consider both happy path and error scenarios
- Account for testing, documentation, and deployment
- Identify clear success criteria
- Ensure plans are maintainable and adaptable
